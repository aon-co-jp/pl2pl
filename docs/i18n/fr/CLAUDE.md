# pl2pl – notes de développement
- **Rôle** : un outil qui récrit du code entre langages, frameworks et systèmes d'exploitation (fait en Rust, dans `src/`). Les langages sources sont listés dans `docs/LANGUAGES.md`, les combinaisons dans `docs/COMBINATIONS.md`. Le propriétaire écrit la conception dans `docs/DESIGN.md`, petit à petit. **Ne jamais inventer la spécification à sa place.**
- **Orientation** : récrire « du plus grand nombre vers le plus grand nombre » entre langages connus. Ne pas tout construire d'un coup ; commencer par ce qui a été choisi. Le site web ne propose que des guides et des téléchargements. La réécriture se fait dans l'application PC.
- **Règles** : ce qui ne peut pas être récrit reste en `TODO` et est signalé (ne jamais le cacher). Rester prudent (en cas de dépendance ou d'effet de bord possible, ne rien changer). Exécuter pour de vrai avant de dire « terminé ». Pas de nouveau REST. Répondre uniquement en japonais.
- **Forme commune (IR)** : `src/ir.rs` (types, contenu des fonctions, modèles, middlewares, gabarits) et, côté écriture, `src/ir_emit.rs`. Le côté entrée (PHP, Python, Java) et le côté sortie (JSON, OpenAPI, FastAPI) sont séparés, ce qui facilite l'ajout de nouvelles paires. `pl2pl php` passe lui aussi par la même écriture ; pour un changement qui ne doit pas modifier la sortie, on le prouve par un diff vide de la sortie avant et après. Les fichiers où aucune route n'est trouvée sont signalés. Vérifier la sortie pour de vrai, par exemple avec `py_compile`.
- **PHP** : `src/php.rs`, `src/blade.rs`, `src/middleware.rs`. Test de bout en bout : `tests/run-php.sh` (vrai FastAPI, SQLite, Jinja2). Tests unitaires : `cargo test --release`. Sous WSL : `wsl -d Ubuntu -- bash <file>`.
- **Mise à jour automatique** : `pl2pl watch` (`src/watch.rs`, `registry/ecosystem.toml`). Les éléments sans commande de vérification sont seulement affichés comme « non vérifiés » et ne sont jamais mis à jour tout seuls. Les alertes passent par `--notify-file` de version-control.
- **Déploiement** : la page de présentation est `webpage/index.html`. Sur le VPS : `/root/easy-web.tokyo/pl2pl` (mise à jour par `git pull` ; page statique, donc pas de redémarrage), `pl2pl-web.service` sur le port 8142, déjà ajouté à `domains.toml`.
- **Pièges** : écrire les fichiers contenant du japonais avec Python `-X utf8`. Garder les scripts shell en LF. Git Bash réécrit les chemins `/mnt/...`. Pour les textes pleins de guillemets ou de `\`, utiliser les outils Write / Edit, pas un heredoc.
- **COBOL_to / Java_to** : déjà intégrés dans `converters/`. Supprimer les dépôts d'origine est irréversible : demander d'abord l'accord final.
- **Système de traduction** (langue humaine) : séparé des convertisseurs. Les convertisseurs ne s'appuient pas sur un LLM.
- **Langues de la documentation** : les fichiers japonais sont les originaux. Les fichiers anglais ont été récrits en mots simples. Les autres langues dans `docs/i18n/` sont des traductions par IA (pas encore relues par des locuteurs natifs). Historique plus ancien : `docs/HISTORY-ja.md`.

## Nouveautés de la v0.2.1 (2026-11-20)
- Si l'on choisit `rpoem` / `rporea` dans `pl2pl web --backend`, des avis s'affichent (japonais et anglais) : RPoem inclut déjà les fonctions compatibles Tauri et WunderGraph Cosmo, tokio et WASM, donc ne pas les choisir en plus ; HTML5 et CSS3 sont utilisés mais en petite quantité ; JavaScript, TypeScript, Node.js et REST ne sont pas utilisés par conception. Ce qu'on ajoute avec `--also` et qui est déjà inclus est refusé (code de sortie 2) ; ce qui est inclus mais pas encore mûr reste sélectionnable, avec une mise en garde.
- `pl2pl maturity [--repo DIR] [--llm URL] [--apply]` juge cette maturité en lançant des tests-sondes (registre : `registry/maturity.toml`). L'avis de l'IA d'aruaru-llm ne change jamais seul le verdict.
- Avec les piles autres que RPoem / RPoRea, `--also nodejs` (ou `next.js`) est accepté avec un avis : nous n'imposons pas notre règle « pas de Node.js », mais nous ne le recommandons pas. Des alternatives adaptées au langage choisi sont listées (RPoem / RPoRea + Reaxt, FastAPI + Jinja2, RS-Node.js, et d'autres que nous n'avons pas vérifiées).
- Dépôts frères développés ensemble : Reaxt, RPoRea, RPoem, RMojo, open-cosmo, RS-TypeScript, RS-JavaScript, RS-Node.js et pl2pl. Quand l'un change, les autres sont vérifiés le jour même.
- `pl2pl info [ui|nojs|json|connect|shared] [--lang ...]` et `webpage/info.html` expliquent les principes de conception de RPoRea / RPoem, avec avantages et inconvénients, en 11 langues.
- Les originaux `COBOL_to` / `Java_to` sont conservés (non supprimés) ; les copies fusionnées dans `converters/` ont donné une sortie identique.

## 2026-11-25 Ajout : prise en charge de @Mapping de MapStruct

Les `@Mapping(target=..., source="a.b")` (attribut source imbriqué), `ignore=true` et `constant="..."` placés sur les méthodes d'un mappeur sont désormais transmis à `MapperBase._to(cls, src, rename, ignore, const)` dans le Python généré. Cela est couvert par le test unitaire `mapstruct_mapping_annotations` (Java_to : 41 réussis) et par une vérification à l'exécution (`owner.name` → `fullName`, ignore, constante). Reste à faire : la forme imbriquée `@Mappings({...})`, `expression=`, `@MappingTarget` et le démarrage avec une vraie base de données.

## Politique d'API Versionless, sans version (2026-11-25)
Les API de ce dépôt sont **Versionless** : pas de `v1` ni équivalent dans les URL ou les noms de paquets ; elles évoluent en ajoutant seulement, sans casser la compatibilité. On ne fait qu'ajouter des champs ; les champs ajoutés sont facultatifs ; les champs inconnus sont ignorés ; pour renommer, on ajoute le nouveau nom et on déclare l'ancien obsolète (délai par défaut : 6 mois ou plus, suppression seulement après avoir confirmé que plus rien ne l'utilise) ; les enum acceptent les valeurs inconnues ; les correctifs urgents de sécurité font exception. Les noms `.v1` existants restent pour l'instant afin de ne pas casser les appelants ; on ajoute un alias sans version et on retire `.v1` par étapes. Détails et sources : fin de [`runo/API-POLICY.md`](https://github.com/aon-co-jp/runo/blob/main/API-POLICY.md). La mise en œuvre se fait étape par étape.

## Politique d'API : abandon total de REST, vers gRPC / Connect
Ce dépôt **ne crée aucune nouvelle API REST**. Les API appelées depuis un navigateur ou `curl` utilisent des **appels simples Connect** (`POST /<paquet>.<Service>/<Method>`, `content-type: application/json`) ; entre services, on utilise **gRPC / gRPC-web**. GraphQL est en lecture seule. Le REST existant est migré quand on y touche, et l'ancienne route est supprimée après la migration. Le JSON se lit avec RS-JSON (`from_str_secure` / `parse_secure`). Les seules exceptions sont les cas où la forme est dictée par la norme de l'autre partie (ACME, rappels OAuth/OIDC, webhooks de tiers, contrôles de santé, fichiers statiques, OTLP). En cas de doute, choisir Connect. Source de référence : le lien ci-dessus.
